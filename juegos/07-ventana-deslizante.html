Entrega 7: ventana deslizante

0 de 6 resueltos

Una ventana deslizante es un tramo de elementos seguidos que se mueve por la lista: al avanzar un paso entra un elemento por un lado y sale otro por el otro, así que puedes actualizar la suma sin volver a recorrer el tramo entero. Unas veces la ventana tiene un tamaño fijo y otras crece y encoge según una condición, como no pasarse de un presupuesto. En SQL la misma idea son las funciones de ventana, como ROW_NUMBER, SUM(...) OVER o LAG, que calculan algo para cada fila mirando las filas de su alrededor sin agruparlas en una sola (SQLite las admite desde la versión 3.25, que ya trae cualquier Python reciente).

Cómo practicar

  1. Descarga el archivo y ábrelo en tu editor.
  2. Completa las funciones y las consultas.
  3. Ejecuta python entrega_07.py para ver qué casos pasan. Solo necesitas Python: SQLite viene incluido.
  4. Si te atascas, pide una pista. Al terminar, compara con la solución.

1. La media de tres días

Escribe media_movil para que devuelva una lista con la media de cada tramo de k valores seguidos de valores, redondeada a 1 decimal con round. El primer tramo va de la posición 0 a la k - 1, el segundo empieza en la 1, y así hasta el último tramo completo. Si no hay ningún tramo completo, devuelve una lista vacía. k siempre es mayor que 0.

  • media_movil([10, 12, 15, 13, 11], 3) devuelve [12.3, 13.3, 13]
  • media_movil([2, 4, 6, 8], 2) devuelve [3, 5, 7]
  1. Con 5 valores y tramos de 3 hay 3 tramos. Antes de escribir el bucle, piensa cuántos tramos salen con n valores y tramos de k.
  2. Calcula la suma del primer tramo una vez. Para pasar al siguiente no hace falta volver a sumarlo entero: un valor entra y otro sale.
  3. Prueba tu bucle mentalmente con la lista de un solo elemento y k = 1: si el último tramo se queda fuera, revisa el límite del range.
Ver solución 
def media_movil(valores, k):
    if k > len(valores):
        return []
    suma = sum(valores[:k])
    medias = [round(suma / k, 1)]
    for i in range(k, len(valores)):
        suma += valores[i] - valores[i - k]
        medias.append(round(suma / k, 1))
    return medias

Con n valores hay n - k + 1 tramos: la versión que recorre range(len(valores) - k) pierde siempre el último, y con los ejemplos de arriba ya se nota. La solución suma el primer tramo y luego, en cada paso, suma el valor que entra y resta el que sale, así que cada valor se toca dos veces como mucho aunque k sea grande. Sumar cada tramo con sum(valores[i:i + k]) también es correcto si el range llega a len(valores) - k + 1, solo que hace más trabajo.

2. El acumulado de cada tienda

Cada fila de ventas es lo que vendió una tienda en un día, y no hay dos filas de la misma tienda con la misma fecha. Muestra tienda, fecha y una columna acumulado con el total vendido por esa tienda desde su primer día hasta esa fecha, incluida. Ordena por tienda y, dentro de cada tienda, por fecha.

  1. Con GROUP BY perderías las filas de cada día: aquí quieres conservar todas y añadir a cada una un total que mira hacia atrás.
  2. Después de SUM(importe) puedes escribir OVER (...) y, dentro de los paréntesis, decir cómo se reparten y cómo se ordenan las filas que entran en la suma.
  3. Necesitas dos cosas dentro del OVER: que cada tienda lleve su propia cuenta, empezando de cero, y que la cuenta avance por fecha. Mira qué hacen PARTITION BY y ORDER BY ahí dentro.
Ver solución 
SELECT tienda, fecha,
       SUM(importe) OVER (PARTITION BY tienda ORDER BY fecha) AS acumulado
FROM ventas
ORDER BY tienda, fecha;

PARTITION BY tienda hace que cada tienda empiece su suma desde cero, y el ORDER BY de dentro del OVER convierte la suma en acumulada: cada fila suma las de su tienda con fecha menor o igual. Sin la partición, el acumulado del Norte arrastra también las ventas del Centro. El ORDER BY final es otro distinto: solo decide cómo se muestran las filas, y por eso hace falta aunque ya haya uno dentro del OVER.

3. La mejor semana corta

Tienes las ventas de cada día en una lista. Escribe mayor_suma para que devuelva la mayor suma de k días seguidos. Las ventas pueden ser negativas, porque cuentan las devoluciones. Si hay menos de k días, devuelve None. k siempre es mayor que 0.

  • mayor_suma([3, 1, 4, 1, 5, 9, 2], 3) devuelve 16
  • mayor_suma([10, -5, 20, 1], 2) devuelve 21
  1. Empieza con la suma de los primeros k días: ya es una candidata a mejor suma.
  2. Al mover la ventana un día a la derecha, entra el día nuevo y sale el que quedó atrás k posiciones; no hace falta volver a sumar los demás.
  3. ¿Con qué valor inicial empiezas a buscar el máximo? Piensa en una semana en la que todos los días hubo más devoluciones que ventas.
Ver solución 
def mayor_suma(ventas, k):
    if len(ventas) < k:
        return None
    actual = sum(ventas[:k])
    mejor = actual
    for i in range(k, len(ventas)):
        actual += ventas[i] - ventas[i - k]
        mejor = max(mejor, actual)
    return mejor

La ventana se mueve sumando el día que entra y restando el que sale, así que cada día se mira una vez aunque k sea grande. La trampa está en el valor inicial del máximo: empezar en 0 parece inocente, pero si todas las ventanas suman en negativo la función devuelve 0, una suma que no existe. Empezar con la suma de la primera ventana real evita el problema sin tener que inventar un valor como -infinito.

4. El primer pedido

Muestra el primer pedido de cada cliente: cliente, fecha e importe, ordenado por cliente. Si un cliente hizo dos pedidos el mismo día, cuenta como primero el de id menor, y cada cliente debe salir una sola vez.

  1. Numera los pedidos de cada cliente del más antiguo al más reciente: el primero de cada uno es el que lleva el número 1.
  2. Hay varias funciones de ventana que numeran filas. Fíjate en qué hace cada una cuando dos filas empatan en el orden: unas repiten número y otras no.
  3. Una función de ventana no se puede usar directamente en el WHERE de la misma consulta. Calcula el número en una subconsulta y filtra desde fuera.
Ver solución 
SELECT cliente, fecha, importe
FROM (
    SELECT cliente, fecha, importe,
           ROW_NUMBER() OVER (PARTITION BY cliente ORDER BY fecha, id) AS n
    FROM pedidos
)
WHERE n = 1
ORDER BY cliente;

ROW_NUMBER da 1, 2, 3... dentro de cada cliente sin repetir nunca un número, y el id en el orden decide los empates de fecha. RANK da el mismo número a las filas empatadas, así que dos pedidos del mismo primer día salen los dos con 1 y el cliente aparece dos veces; con la primera tabla no se nota porque no hay empates. Filtrar en una consulta exterior es obligatorio, porque el WHERE se evalúa antes que las funciones de ventana.

5. Los días dentro del presupuesto

Tienes lo que gastaste cada día (números enteros, nunca negativos) y un presupuesto. Escribe racha_en_presupuesto para que devuelva cuántos días seguidos, como máximo, puedes juntar sin que su gasto total pase del presupuesto. Gastar exactamente el presupuesto está permitido. Si ningún día cabe por sí solo, devuelve 0.

  • racha_en_presupuesto([4, 1, 1, 3], 5) devuelve 3
  • racha_en_presupuesto([2, 3, 1, 1, 5, 1], 6) devuelve 3
  1. Usa una ventana de tamaño variable: un índice marca dónde empieza y el bucle va añadiendo días por el final mientras lleva la suma.
  2. Cuando la suma se pasa del presupuesto, no tires toda la ventana: quita días por el principio, uno a uno, hasta que vuelva a caber.
  3. A veces hay que quitar más de un día para volver a caber, y a veces la ventana se queda vacía. Después de ajustarla, su longitud es una candidata a la mejor.
Ver solución 
def racha_en_presupuesto(gastos, presupuesto):
    inicio = 0
    suma = 0
    mejor = 0
    for fin, gasto in enumerate(gastos):
        suma += gasto
        while suma > presupuesto:
            suma -= gastos[inicio]
            inicio += 1
        mejor = max(mejor, fin - inicio + 1)
    return mejor

La ventana crece por la derecha y encoge por la izquierda solo lo justo para volver a caber; como los gastos no son negativos, quitar días nunca hace que la suma suba. Empezar la ventana de cero en el día que se pasa parece razonable, pero tira días del principio que todavía cabían: con [4, 1, 1, 3] y presupuesto 5 se pierde la racha 1, 1, 3, y además cuenta como racha un día que por sí solo ya se pasa. Aunque hay un while dentro del for, cada día entra y sale de la ventana una sola vez.

6. Las subidas de precio

La tabla precios guarda el precio de un producto en las fechas en que se revisó, que no siempre son días seguidos. Muestra la fecha y la subida (precio de esa fecha menos el de la revisión anterior) de las revisiones en que el precio subió respecto a la anterior, ordenadas por fecha. La primera revisión no tiene anterior, así que no puede salir.

  1. Para cada fila necesitas el precio de la fila anterior por fecha, que no es lo mismo que el precio del día anterior en el calendario.
  2. Hay una función de ventana que devuelve el valor de una columna en la fila previa según el orden que indiques. En la primera fila devuelve NULL.
  3. Calcula la diferencia en una subconsulta y filtra fuera las que sean positivas. Una comparación con NULL nunca es verdadera, así que la primera fila se descarta sola.
Ver solución 
SELECT fecha, subida
FROM (
    SELECT fecha,
           precio - LAG(precio) OVER (ORDER BY fecha) AS subida
    FROM precios
)
WHERE subida > 0
ORDER BY fecha;

LAG(precio) OVER (ORDER BY fecha) trae el precio de la revisión anterior, haya pasado un día o una semana. Unir la tabla consigo misma buscando la fecha de ayer funciona mientras las revisiones son diarias, pero en cuanto falta un día esa fila se queda sin pareja y su subida desaparece del resultado. La resta con NULL da NULL y NULL > 0 no es verdadero, por eso la primera revisión no sale. date(..., '-1 day') es propio de SQLite; LAG vale igual en PostgreSQL, MySQL 8 y SQL Server.
